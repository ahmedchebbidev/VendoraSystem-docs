MCP M3 — connexion OAuth 2.1 « en un clic » (11/11/2026) ​

Dossier docs/captures/2026-11-11-mcp-m3 · 0 image(s) · 0 trace(s)

Preuves du lot M3 (spec 18 RG-MCP-30 à 48, fiche docs/lots/mcp-m3.md) : écrans nouveaux du back-office et transcription d'un client OAuth complet joué en local.

Stack jetable : serveur Vendora de la branche mcp-m3 (port 8095, base pos_m3 supprimée après coup), serveur MCP (port 8195, VENDORA_MCP_PUBLIC_URL=http://localhost:8195/mcp), back-office (ng serve, port 4215). Commerce fictif « Le Petit Bistrot (démo) » semé par help/tools/seed/seed-demo.py, compte bistrot.m3@vendora.test. Aucun jeton, code, identifiant de demande, cookie ni mot de passe dans ce dossier. Captures 01 à 07 du 11/11/2026 ; captures 08 et 09 et transcription refaites le 12/11/2026, après la relecture de sécurité.

Limite de cette preuve : tout est local. Aucun essai depuis claude.ai, l'application téléphone, ChatGPT ou Claude Code en conditions réelles — voir « Ce qui reste à Ahmed » en bas de page.

Mêmes images que le centre d'aide (help/public/captures/reglages/connecter-un-assistant/ et …/cles-api/). Suffixes : .en / .ar = langue (l'arabe est en droite à gauche), .sombre = thème sombre ; sans suffixe = français, thème clair. Largeur bureau, sauf 06 (téléphone, 375 px).

Preuve de bout en bout (client OAuth complet, en local) ​

python3 mcp/tools/oauth-e2e.py --accounts <comptes de démo> --mcp http://localhost:8195/mcp — bibliothèque standard seulement. Le script joue ce que fait Claude : il part du 401 du serveur MCP, découvre le serveur d'autorisation, s'enregistre, demande l'autorisation par l'origine du back-office en gardant le cookie reçu comme un navigateur, obtient le consentement par l'API du back-office (compte de démo), échange le code, appelle des outils, puis éprouve rotation, rejeu, révocations, refus et journal d'audit. Sortie telle quelle (les secrets y sont remplacés par « … » par le script lui-même) :

71 vérifications réussies sur 71.

Ce que la transcription établit : la découverte part bien du 401 ; le point d'autorisation est sur l'origine du back-office ; une redirection inconnue n'est jamais suivie et un client non vérifié ne reçoit aucune erreur par redirection (pas de redirection ouverte) ; sans le cookie du navigateur d'origine, ou avec un autre, la demande ne se lit ni ne s'autorise (403) ; un paramètre en double, ou un paramètre dans l'adresse du point de jeton, est refusé ; le nom « Claude » pris par un client non vérifié est remplacé par son domaine ; refus, révocations et rejeu figurent au journal d'audit avec leur motif ; PKCE plain et un resource inconnu sont refusés ; l'adresse du back-office ne porte que l'identifiant opaque ; le jeton ne voit que la famille cochée (8 outils, anti-fraude absente) ; un renouvellement rejoué et un code rejoué révoquent la connexion ; les deux révocations coupent l'accès dès la requête suivante.

Autre vérification réelle faite le 11/11/2026 : le serveur local a lu le document client de Claude Code (https://claude.ai/oauth/claude-code-client-metadata) et l'a reconnu (nom « Claude Code », domaine claude.ai, redirections http://localhost/callback et http://127.0.0.1/callback) — c'est la capture 01.

Essai avec Claude Code (non fait : il faut un humain devant le navigateur) ​

  1. Serveurs locaux en marche (API, MCP avec VENDORA_MCP_PUBLIC_URL=http://localhost:<port>/mcp, back-office), ou le staging une fois déployé.
  2. claude mcp add --transport http vendora http://localhost:<port>/mcp — sans en-tête de clé.
  3. Dans une session Claude Code : /mcp → vendora → Authenticate. Le navigateur s'ouvre sur /connecter-assistant ; se connecter au back-office si besoin.
  4. Vérifier « Claude Code », claude.ai, Vérifié, retour vers « une application installée sur cet ordinateur » ; choisir magasins et familles ; Autoriser.
  5. /mcp doit lister les outils ; poser « Combien ai-je vendu hier ? ». Puis Retirer l'accès dans Réglages › Clés d'API › Assistants connectés : l'appel suivant doit demander une reconnexion.
  6. Nettoyer : claude mcp remove vendora.

Pas-à-pas :

  1. Déployer main (API, MCP, back-office), poser les cinq variables, redéployer l'API et le MCP.
  2. Réveiller les deux services (plan gratuit) : ouvrir https://vendora-api-staging.onrender.com/.well-known/oauth-authorization-server et https://vendora-mcp-staging.onrender.com/.well-known/oauth-protected-resource/mcp — les deux doivent répondre du JSON, et resource doit être exactement l'adresse du MCP.
  3. Sur claude.ai : Réglages › Connecteurs › Ajouter un connecteur personnalisé → https://vendora-mcp-staging.onrender.com/mcp → Connecter.
  4. Sur la page Vendora : se connecter (compte propriétaire d'un commerce de démo), lire le nom et le domaine affichés, choisir un magasin et « Ventes et rapports », Autoriser. Attendu au premier essai : « Non vérifié », affiché sous le domaine claude.ai — « Vérifié » demande désormais l'identifiant client exact, et celui du site claude.ai n'est pas connu (seuls ceux de Claude Code et de ChatGPT sont dans la liste par défaut). Relever l'identifiant vu par le serveur (colonne client_id de la demande, ou journal) et, s'il est stable et servi par claude.ai, l'ajouter à POS_OAUTH_VERIFIED_CLIENT_IDS. Si l'écran dit « ouverte dans un autre navigateur », le relais du back-office ne transmet pas le cookie : voir deploy/README.md § 8.
  5. Sur le téléphone, dans l'application Claude : « Fais-moi le bilan d'hier » ; puis Retirer l'accès dans Réglages › Clés d'API › Assistants connectés et vérifier que Claude demande de se reconnecter.
