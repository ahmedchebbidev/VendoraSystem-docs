Déploiement de Vendora — environnements dev, test (staging) et prod ​

Paquet indépendant de l'hébergeur : n'importe quelle machine (ou VM) avec Docker Engine et Docker Compose v2 suffit. Aucun service propre à un cloud n'est utilisé. Les adresses exemple.test des modèles sont fictives.

FichierRôle
server/DockerfileImage du serveur : build Gradle (JDK 21) → JRE 21, utilisateur non root, sonde /actuator/health
deploy/web.DockerfileImage web : back-office (web/) + Console (console/) construits par ng build, servis par nginx
deploy/nginx/nginx : back-office sur /, Console sur un hôte séparé, /api/ et /r/ relayés au serveur (même origine → pas de CORS), en-têtes de sécurité

Le garde-fou (EnvironmentGuard, avant la création des beans) liste toutes les variables à corriger d'un coup, sans jamais afficher leurs valeurs :

Démarrage refusé en environnement « prod » — variables à corriger (voir deploy/README.md) :

Un POS_ENVIRONMENT=dev oublié ne désarme jamais le profil prod (le plus strict l'emporte). La Console affiche aussi l'environnement dans « Avant la mise en production ».

2. Lancer un environnement ​

Toutes les commandes se lancent depuis la racine du dépôt.

sh
# Test / recette
cp deploy/env/staging.env.example deploy/env/staging.env
#   → remplacer chaque « change-me… » (openssl rand -base64 48 pour les clés, openssl rand -base64 32 pour
#     POS_PAYMENTS_CREDENTIALS_KEY), renseigner les hôtes et les adresses
docker login ghcr.io                     # une fois par machine, voir §9 (paquets privés)
docker compose -f deploy/docker-compose.staging.yml --env-file deploy/env/staging.env up -d

# Production
cp deploy/env/prod.env.example deploy/env/prod.env      # mêmes remplacements, secrets DIFFÉRENTS de la recette,
                                                         # VENDORA_VERSION épinglée (X.Y.Z ou sha-…)
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env up -d

# Variante sans registre : construire les images sur la machine (sources du dépôt)
docker compose -f deploy/docker-compose.prod.yml -f deploy/docker-compose.build.yml \
  --env-file deploy/env/prod.env up -d --build

# État, journaux
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env ps
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env logs -f server

--env-file alimente les valeurs du fichier compose (mots de passe PostgreSQL, hôtes nginx, port publié) ; le même fichier est passé au conteneur serveur (env_file). PostgreSQL ne reçoit que ses mots de passe, nginx que ses hôtes.

HTTPS : le conteneur web écoute en HTTP (port VENDORA_HTTP_PORT). Terminer le TLS devant lui — répartiteur de charge de l'hébergeur ou reverse proxy de la machine — pour les deux hôtes (VENDORA_APP_HOST, VENDORA_CONSOLE_HOST), en transmettant X-Forwarded-Proto: https. Les deux noms doivent pointer vers la machine.

Apps caisse / borne : elles appellent l'API à l'adresse du back-office (https://<VENDORA_APP_HOST>/api/…).

3. Premier administrateur de la Console ​

Le premier administrateur ne se crée jamais par l'API (spec 17 RG-PLAT-04, docs/PRODUCTION.md §4) : on lance une seconde instance éphémère du serveur avec la commande, qui affiche le lien de configuration (72 h, mot de passe + double authentification) puis s'arrête.

sh
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env run --rm server \
  --create-platform-admin=vous@exemple.test --platform-admin-name="Prénom Nom"

Le lien pointe vers POS_CONSOLE_URL. Commande refusée dès qu'un administrateur existe (actif ou invité).

4. Sauvegarde et restauration PostgreSQL ​

sh
# Sauvegarde (format custom, compressé) — à planifier (cron de la machine) et à copier HORS de la machine
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env exec -T postgres \
  pg_dump -U pos -d pos -Fc > vendora-$(date +%Y%m%d-%H%M).dump

# Restauration dans une base vide (serveur arrêté)
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env stop server
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env exec -T postgres \
  pg_restore -U pos -d pos --clean --if-exists < vendora-AAAAMMJJ-HHMM.dump
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env start server

Les rôles (pos_app, pos_platform) sont globaux au cluster : ils ne sont pas dans le dump. Sur un volume neuf, le script deploy/postgres/10-vendora-roles.sh les recrée au premier démarrage. Garder aussi deploy/env/prod.env (en particulier POS_PAYMENTS_CREDENTIALS_KEY, sans laquelle les identifiants des connecteurs sont illisibles) dans un coffre à secrets.

Changer un mot de passe de base : ALTER ROLE pos_app WITH PASSWORD '…'; (idem pos_platform, ou celui du propriétaire pos) via docker compose … exec postgres psql -U pos -d pos, puis mettre à jour deploy/env/*.env et redémarrer le serveur. Les variables POS_DB_* ne sont lues par PostgreSQL qu'au premier démarrage du volume.

5. Mise à jour ​

sh
# 1. VENDORA_VERSION=<nouvelle version> dans deploy/env/prod.env (ex. 1.4.0 ou sha-1a2b3c4, voir §9)
# 2. tirer les images puis recréer les conteneurs qui changent
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env pull server web
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env up -d

Retour arrière : remettre l'ancienne VENDORA_VERSION et relancer les deux commandes (une migration Flyway déjà appliquée n'est pas annulée : restaurer la sauvegarde si la nouvelle version a migré la base). Les fichiers compose et deploy/ eux-mêmes viennent du dépôt (git pull si on les a modifiés).

Les migrations Flyway s'appliquent automatiquement au démarrage du serveur (propriétaire pos) ; une migration en échec arrête le démarrage sans servir de trafic. Faire une sauvegarde (§4) avant chaque mise à jour. Les apps caisse plus anciennes que pos.app.min-version reçoivent 426 et continuent hors ligne.

Les images viennent de GitHub Container Registry (§9) ; avec la surcharge docker-compose.build.yml, elles sont construites sur la machine (git pull puis up -d --build).

6. Vérifications après déploiement ​

  • curl https://<VENDORA_APP_HOST>/api/v1/public/environment → l'environnement attendu ;
  • curl https://<VENDORA_APP_HOST>/actuator/health n'est pas relayé (seuls /api/, /r/, la doc OpenAPI) : la sonde est lue par Docker dans le conteneur (docker compose … ps → healthy) ;
  • Console › tableau de bord › « Avant la mise en production » : tous les points au vert ;
  • Console › Paramètres › Emails : email de test.

7. Pré-staging : la recette sur le Mac, publiée par Cloudflare Tunnel (gratuit) ​

Pour tester les vrais iPhone, iPad et tablettes Android et le web depuis n'importe quel réseau, sans hébergeur : la pile de recette (profil staging, base PostgreSQL à part de celle de dev) tourne dans Docker sur le Mac, et deux tunnels Cloudflare la publient en HTTPS. Rien n'est ouvert sur la box : les tunnels sortent du Mac.

sh
scripts/prestaging.sh up            # 1re fois : secrets générés dans deploy/env/prestaging.env, images construites
scripts/prestaging.sh urls          # adresses publiques du back-office (= API des apps) et de la console
scripts/prestaging.sh admin moi@exemple.fr "Prénom Nom"   # premier administrateur de la console (lien affiché)
scripts/prestaging.sh logs server   # journaux ; emails en mode MOCK = écrits ici (liens d'invitation compris)
scripts/prestaging.sh down          # arrêt (données gardées) ; reset = arrêt + base effacée
  • Adresses : sans compte, les tunnels « rapides » donnent des adresses https://…trycloudflare.com nouvelles à chaque up (le script les relit et les passe au serveur : emails, QR d'appairage). Pour des adresses fixes : compte Cloudflare + domaine, tunnel nommé (Zero Trust › Tunnels), deux public hostnames vers http://web:80 avec l'option HTTP Host Header = app.prestaging.internal et console.prestaging.internal, puis CLOUDFLARE_TUNNEL_TOKEN, PRESTAGING_APP_URL, PRESTAGING_CONSOLE_URL dans deploy/env/prestaging.env.
  • Apps : build « POS Staging » (Android assembleStaging, iOS schéma PosApp Staging) ; à l'appairage, scanner le QR de l'assistant (il porte l'adresse du tunnel) ou saisir l'adresse du back-office comme URL du serveur. Un vrai iPhone demande la signature Xcode avec ton Apple ID (compte gratuit : app valable 7 jours).
  • Limites : le Mac doit rester allumé ; les tunnels rapides sont faits pour le test (pas de garantie de service) ; données de test uniquement — paiements, e-reporting, SMS et push simulés, emails écrits dans les journaux.

8. Staging sur Render (gratuit) + base Neon ​

Le fichier render.yaml (Blueprint) décrit quatre services, déployés à chaque push sur main :

ServiceTypeAdresse
vendora-api-stagingserveur (Docker, plan gratuit, Francfort)https://vendora-api-staging.onrender.com — URL du serveur des apps « POS Staging »
vendora-backoffice-stagingsite statique (/api/, /r/ relayés au serveur)https://vendora-backoffice-staging.onrender.com
vendora-console-stagingsite statique (/api/ relayé)https://vendora-console-staging.onrender.com
vendora-mcp-stagingserveur MCP (Docker, plan gratuit, lecture seule, sans état ni secret)https://vendora-mcp-staging.onrender.com/mcp — à relier sans clé par OAuth (claude mcp add --transport http vendora https://vendora-mcp-staging.onrender.com/mcp, puis /mcp), ou avec une clé « Assistant IA » : claude mcp add --transport http vendora https://vendora-mcp-staging.onrender.com/mcp --header "X-API-Key: <clé>" (voir mcp/README.md)

Mise en place (une fois) :

  1. Neon (gratuit, région Europe — Francfort) : créer un projet vendora-staging, copier la chaîne de connexion du rôle propriétaire (onglet Connect), puis créer les rôles de Vendora :
    sh
    NEON_OWNER_URL='postgresql://neondb_owner:…@….eu-central-1.aws.neon.tech/neondb?sslmode=require' deploy/neon/init-roles.sh
    Le script affiche POS_DB_URL, POS_DB_OWNER_USER, POS_DB_OWNER_PASSWORD, POS_DB_APP_PASSWORD, POS_PLATFORM_DB_PASSWORD (à garder dans un gestionnaire de mots de passe). La base gratuite de Render n'est pas utilisée : elle est supprimée 30 jours après sa création.
  2. Render — deux façons :
    • par l'API (fait le 07/11/2026) : clé d'API Render dans ~/.config/vendora/render-api-key, accès GitHub accordé à Render, puis python3 -I deploy/render/create-services.py --project Vendora --environment Staging (crée les services dans l'environnement du projet, laisse intacts ceux qui existent). Ne pas créer en plus un Blueprint avec les mêmes noms ;
    • par le Blueprint : New › Blueprint, choisir le dépôt GitHub (branche main) ; Render lit render.yaml, génère les clés (POS_AUTH_JWT_SECRET, POS_PLATFORM_JWT_SECRET, POS_PAYMENTS_CREDENTIALS_KEY) et demande les cinq variables de la base. Si un nom de service est déjà pris, Render ajoute un suffixe : corriger les adresses dans render.yaml et POS_SERVER_URL_STAGING / posServerUrlStaging des apps.
  3. Premier administrateur de la console (pas de shell en plan gratuit) : copier dans deploy/env/render-staging.env (ignoré par git) les variables du service Render (base Neon, clés, adresses), puis lancer depuis le Mac l'image du serveur contre la base Neon :
    sh
    docker run --rm --env-file deploy/env/render-staging.env -e SPRING_PROFILES_ACTIVE=staging \
  ghcr.io/ahmedchebbidev/vendora-server:main \
  --create-platform-admin=moi@exemple.fr --platform-admin-name="Prénom Nom"
    Le lien de configuration (mot de passe + double authentification) s'affiche ; les membres suivants s'invitent depuis la console.

Connexion OAuth des assistants (carte MCP M3) : cinq variables, déjà dans render.yaml et create-services.py — à ajouter à la main sur les services qui existent déjà (le script laisse intacts les services existants) :

Démonstration publique /demo/mcp (carte MCP U5) — éteinte par défaut, à activer avec l'accord d'Ahmed :

  1. créer le commerce fictif sur le staging : help/tools/seed/seed-demo-public.py avec --key-rate 960 (chaque requête de démo coûte 2 à 4 appels à l'API ; plafond global de la démo : 240 / min) ; la clé est écrite hors du dépôt (--key-out) ;
  2. poser VENDORA_DEMO_API_KEY sur vendora-mcp-staging dans le tableau de bord Render (jamais dans le dépôt) ;
  3. vérifier : curl -s -X POST https://vendora-mcp-staging.onrender.com/demo/mcp -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' répond sans 401, sans fraud_alerts ;
  4. mesurer le nombre de relais : si deux visiteurs de réseaux différents reçoivent 429 ensemble, l'adresse retenue est celle d'un relais — passer VENDORA_MCP_DEMO_TRUSTED_PROXIES à 2 ;
  5. poser les deux secrets GitHub de la tâche nocturne demo-nightly.yml.

Couper : VENDORA_MCP_DEMO_ENABLED=false (ou retirer la clé). Une démo en 503 : lire apiError dans le journal du service (clé expirée, arrêt d'urgence du commerce de démo, formule). Détails : mcp/README.md.

Plafonds OAuth (lot « Plafonds OAuth », RG-MCP-74 → 77) — variables facultatives de vendora-api-staging ; sans elles les défauts ci-dessous s'appliquent. Aucune ne touche la vente, la synchronisation ni les Z. Un « réseau » est le /24 d'une adresse IPv4 ou le /48 d'une adresse IPv6 (même découpage que le serveur MCP) ; la base ne garde que ce réseau, jamais l'adresse.

VariableDéfautRôle
POS_OAUTH_TRUSTED_PROXIES0Nombre de relais de confiance devant l'API, pour lire X-Forwarded-For (0 à 10). 0 : l'en-tête n'est jamais cru, l'adresse est celle de la connexion. N : l'appelant est la N-ième entrée en partant de la fin de la chaîne « en-tête + connexion » ; chaîne plus courte ⇒ adresse de la connexion. 0 sur Render (staging, et production) : server.forward-headers-strategy: native y remplace déjà l'adresse de la connexion ; toute autre valeur y est ignorée (0 appliqué) avec une erreur au journal du démarrage

POS_OAUTH_REGISTER_PER_NETWORK_PER_MINUTE5Appels à POST /oauth/register par réseau et par minute. Global : 60 / minute

POS_OAUTH_MAX_PENDING_REQUESTS2000Plafond global des demandes en attente. Atteint : la plus ancienne demande qu'aucun commerçant connecté n'a affichée est évincée pour laisser passer la nouvelle. La moitié de ce plafond au plus (1 000) peut être protégée par un affichage, tous commerces confondus : l'autre moitié reste toujours évinçable ; au-delà, les confirmations des commerces en essai tombent d'abord (les plus anciennes), celles des commerces payants ensuite
POS_OAUTH_MAX_GRANTS_PER_TENANT20Assistants connectés au plus par commerce (connexions ni retirées ni échues, plus les accords dont le code n'est pas encore échangé). Au-delà, l'accord est refusé sur l'écran de consentement (409 OAUTH_TOO_MANY_CONNECTIONS, message en clair : retirer un accès dans Réglages › Assistant IA). Les connexions existantes ne sont jamais coupées par ce plafond
POS_OAUTH_REGISTRATIONS_PER_NETWORK20Enregistrements dynamiques (POST /oauth/register) par réseau et par heure. Au-delà : 429 temporarily_unavailable avec Retry-After
POS_OAUTH_MAX_REGISTERED_CLIENTS3000Plafond global des clients enregistrés. Atteint : le plus ancien client sans connexion vivante (non retirée, non échue, jeton de renouvellement encore valide) ni demande affichée par un commerçant est évincé ; sinon 503. Les clients protégés par une connexion vivante tiennent la moitié du plafond au plus (1 500) : au-delà, un enregistrement au plafond évince un protégé parmi les plus anciens, d'abord celui dont toutes les connexions appartiennent à des commerces sans accès assistant (essai terminé, formule changée) — ses connexions continuent de fonctionner et de se renouveler, seule une nouvelle demande d'accès l'oblige à se réenregistrer. Le ménage suit la même règle (client plus servi depuis un jour) ; les lignes de connexion (audit) ne sont jamais supprimées
POS_OAUTH_DOCUMENTS_PER_NETWORK30Lectures de documents clients (CIMD, appel sortant) par réseau et par heure, une seule à la fois par réseau (3 s au plus chacune, 32 en même temps pour tout le serveur). Un document déjà en cache ne compte pas. En IPv6, deux à la fois au plus pour tout un /32. Les clients de POS_OAUTH_VERIFIED_CLIENT_IDS sont hors quota (ni plafond du réseau, ni éviction du cache) ; si leur document ne peut pas être relu pour cause de panne (injoignable, délai, erreur 5xx, aucune place libre), la copie périmée du cache est servie plutôt qu'un refus, 7 jours au plus après son échéance (le ménage la retire ensuite) — jamais si l'éditeur a répondu autre chose (404, redirection, document invalide) : la demande est alors refusée. Compteur en mémoire, par nœud
POS_OAUTH_MAX_CACHED_DOCUMENTS2000Taille du cache des documents clients. Plein : le document le plus anciennement utilisé est remplacé
POS_OAUTH_REFRESH_GRACE_SECONDS30Fenêtre de grâce du renouvellement (0 à 300). Un jeton de renouvellement déjà échangé, rejoué par le même client dans ce délai, rend la même paire (réponse perdue en route) tant que cette paire n'a pas servi ; au-delà, ou si elle a servi : connexion révoquée et tracée (REPLAY). 0 : tout rejeu révoque
POS_OAUTH_REQUIRE_RESOURCE_HEADERfalsetrue : un jeton vd_oat_ n'est accepté que si l'appel porte X-Vendora-Resource égal à la ressource de son émission. false : l'en-tête est vérifié s'il est présent (valeur différente ⇒ 401), toléré absent. À ne passer à true qu'une fois le serveur MCP déployé avec l'envoi de cet en-tête — sinon toutes les connexions OAuth répondent 401

Débit par minute de l'autorisation et de l'enregistrement : la part d'un réseau (20 et 5) est très inférieure au plafond global (600 et 60), et le plafond global ne refuse que les réseaux déjà au-dessus d'un dixième de leur part dans la minute (2 autorisations, 1 enregistrement) ; un réseau qui n'a encore rien envoyé passe toujours, jusqu'à un plafond dur de cinq fois le global (3 000 et 300 par minute). IPv6 : la même règle s'applique une seconde fois au /32 (un opérateur ou un hébergeur entier), dont la part vaut huit fois celle d'un /48 (16 autorisations, 8 enregistrements par minute) — acheter des milliers de /48 dans un même bloc ne remplit donc plus le plafond dur ; en IPv4 rien ne change. /oauth/token et /oauth/revoke restent plafonnés par adresse et globalement, pas par réseau (un réseau d'entreprise entier renouvelle ses jetons depuis la même adresse) ; « adresse » = l'adresse IPv4 sans son port, ou le /64 d'une adresse IPv6. Les compteurs par minute en mémoire sont purgés à chaque minute et bornés (20 000 clés anonymes par compartiment — autorisation, enregistrement, jeton, révocation, chacun par adresse, par réseau et par /32 — au-delà une case de débordement propre au compartiment : saturer l'un ne touche pas les autres) ; les clés d'API gardent toujours leur propre compteur. Demande « confirmée » (protégée de l'éviction) : seulement si l'utilisateur connecté qui l'affiche pourrait l'accorder (propriétaire ou administrateur, au moins un magasin administré, formule avec l'accès assistant, accès non coupé, ni par le commerce ni par Vendora ; jamais sous délégation Vendora), 3 par commerce au plus et la moitié du plafond global en tout — au-delà, la plus ancienne confirmée d'un commerce en essai (inscription libre non convertie) redevient évinçable, puis seulement la plus ancienne d'un commerce payant. Relais de confiance : la ligne de journal du premier appel anonyme donne l'adresse vue, la présence de l'en-tête, le nombre de relais de confiance appliqué et le réseau retenu. Sur Render la valeur reste 0 : ne pas l'augmenter, même si deux appelants semblent partager un réseau (le signaler plutôt, la cause est ailleurs).

À mesurer sur le staging avant la production (les défauts ci-dessus sont des hypothèses, pas des mesures) :

  1. CGNAT mobile — des centaines d'abonnés d'un opérateur sortent par le même /24 : vérifier sur un téléphone en 4G que 20 autorisations / minute, 60 demandes en attente et 30 lectures de documents / heure par réseau ne refusent pas un commerçant légitime (compter les 429 et les temporarily_unavailable par réseau dans le journal) ;
  2. enregistrement dynamique côté serveur des assistants — un assistant qui enregistre ses clients depuis ses propres serveurs présente quelques réseaux seulement pour tous ses utilisateurs : vérifier que 5 enregistrements / minute et 20 / heure par réseau suffisent, sinon relever POS_OAUTH_REGISTER_PER_NETWORK_PER_MINUTE et POS_OAUTH_REGISTRATIONS_PER_NETWORK ;
  3. chaîne X-Forwarded-For réelle sur Render et IPv6 entrant — relever sur un appel réel ce que Render transmet (Cloudflare est-il devant ? combien d'entrées, laquelle est l'appelant ?) et si les appelants arrivent en IPv6 : la ligne de journal du premier appel anonyme doit montrer l'adresse du téléphone de test, pas celle d'un relais, et deux appelants distincts doivent tomber dans deux réseaux distincts. Vérifier aussi qu'un opérateur IPv6 grand public (un seul /32 pour tous ses abonnés) n'est pas gêné par la part du /32 (16 autorisations / minute au-delà desquelles il dépend du surplus global).

Le back-office n'a aucune variable nouvelle : l'écran de consentement (/connecter-assistant) appelle l'API par le relais /api/ habituel, et le serveur le trouve par POS_BACKOFFICE_URL (déjà posée ; POS_OAUTH_CONSENT_URL ne sert que si l'écran vit ailleurs). Le point d'autorisation passe lui aussi par ce relais : https://vendora-backoffice-staging.onrender.com/api/v1/oauth/authorize — c'est là que le serveur pose le cookie qui lie la demande au navigateur (vd_oauth_nav, HttpOnly, Secure, SameSite=Lax, chemin /api/v1/oauth), relu quand l'écran de consentement appelle /api/v1/oauth/requests/*. Le relais doit donc transmettre tels quels la réponse 302, son en-tête Set-Cookie et l'en-tête Cookie des appels suivants : à vérifier une fois au staging (voir ci-dessous), ce comportement n'a été prouvé qu'avec le proxy de développement. Les autres chemins (/oauth/token, /oauth/revoke, /oauth/register, /.well-known/oauth-authorization-server) sont servis par l'API elle-même. POS_OAUTH_VERIFIED_CLIENT_IDS (défaut : les documents client de Claude et de ChatGPT) n'est à poser que pour changer la liste des assistants affichés « Vérifié » : ce sont des identifiants client exacts (l'adresse du document), pas des noms de domaine. L'identifiant du site claude.ai n'y est pas (il n'est pas connu) : au premier essai il sera affiché « Non vérifié » sous le domaine claude.ai — le relever, puis l'ajouter ici. Vérification après déploiement : curl -s https://vendora-api-staging.onrender.com/.well-known/oauth-authorization-server (l'émetteur doit être l'URL de l'API) et curl -si -X POST https://vendora-mcp-staging.onrender.com/mcp -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' (401 avec resource_metadata). Relais du cookie : curl -si 'https://vendora-backoffice-staging.onrender.com/api/v1/oauth/authorize?response_type=code' doit répondre 302 vers /connecter-assistant?erreur=… (et non la page du back-office) ; puis une vraie connexion depuis un assistant doit afficher l'écran de consentement, pas « ouverte dans un autre navigateur ». Adresse vue derrière le proxy : au premier appel d'un point OAuth anonyme, le journal de l'API écrit une ligne (« OAuth : premier appel anonyme — adresse vue par le serveur : … ») — si elle montre une adresse interne de Render et non celle de l'appelant, le plafond de débit par adresse ne distingue plus les appelants (le plafond global reste actif). Plan gratuit : un service endormi met environ une minute à se réveiller, plus que les 10 secondes que Claude laisse aux points OAuth — ouvrir les deux adresses ci-dessus juste avant de connecter l'assistant, ou passer ces deux services sur un plan sans mise en veille.

Emails : le plan gratuit de Render bloque les ports SMTP (25, 465, 587) ; le staging envoie donc par l'API HTTPS de Brevo (POS_MAIL_MODE=BREVO, POS_MAIL_BREVO_API_KEY — clé d'API xkeysib-…, port 443), mais seulement aux adresses de POS_MAIL_ALLOWED_RECIPIENTS (liste blanche obligatoire en recette) ; un email pour une autre adresse n'est pas envoyé et son texte complet (liens compris) est écrit dans les journaux du service. En mode MOCK (dev, pré-staging), le texte complet de chaque email est aussi écrit au journal. La boîte simulée /api/v1/dev/mails ne répond qu'en dev (404 ailleurs).

Limites du plan gratuit : le serveur s'endort après 15 minutes sans requête et met environ une minute à se réveiller (les caisses en mode hors ligne continuent de vendre et resynchronisent au réveil) ; les tâches planifiées (santé des clients, cycle de vie) ne tournent pas pendant le sommeil ; 750 heures d'instance par mois et par compte ; mémoire réduite (réglages JVM dans render.yaml). Le relais /api/ par les sites statiques ajoute de la latence. Jamais pour la production : elle reste sur un serveur payant (§2).

Render construit lui-même l'image du serveur depuis server/Dockerfile (branche main) : il n'utilise pas GHCR. Pour qu'il tire l'image publiée à la place (déploiement plus rapide, même image que la prod), il faudrait un service de type image et un identifiant de registre (jeton read:packages) dans Render — non fait, le plan gratuit s'en passe.

9. Registre d'images : GitHub Container Registry (GHCR) ​

Le workflow .github/workflows/images.yml construit et publie les deux images à chaque push sur main, à chaque étiquette git v* et à la demande (Actions › Images Docker (GHCR) › Run workflow) :

ImageContenu
ghcr.io/ahmedchebbidev/vendora-serverserveur Spring Boot (server/Dockerfile)
ghcr.io/ahmedchebbidev/vendora-webback-office + Console servis par nginx (deploy/web.Dockerfile)

Étiquettes (les mêmes pour les deux images) :

ÉtiquetteQuandUsage
sha-1a2b3c4chaque commit publié (SHA court)épingler exactement un commit
maindernier commit de main (bouge à chaque push)recette, essais
1.4.0 et 1.4étiquette git v1.4.0production (version publiée)

Pas d'étiquette latest : une machine épingle toujours VENDORA_VERSION. Un autre registre (miroir, fork) se choisit par VENDORA_REGISTRY (défaut ghcr.io/ahmedchebbidev). Chaque image est multi-architecture (linux/amd64 et linux/arm64 : serveurs x86, Graviton / Ampere, Mac Apple Silicon) ; les étapes de build tournent sur l'architecture du runner (le JAR et les fichiers web sont identiques pour les deux), seule l'étape d'exécution existe en deux variantes. Cache de build : cache GitHub Actions (type=gha). Authentification : le GITHUB_TOKEN du run (permission packages: write) — aucun secret à créer. Les pull requests ne publient rien (job docker de ci.yml).

Publier une version :

sh
git tag v1.4.0 && git push origin v1.4.0      # → images 1.4.0, 1.4 et sha-… quelques minutes plus tard

Tirer une image : le dépôt est privé, donc les paquets aussi (un paquet poussé depuis Actions hérite de la visibilité du dépôt et lui est lié). Sur chaque machine, une fois :

sh
# Jeton GitHub « classic » avec la seule portée read:packages (Settings › Developer settings › Personal access tokens),
# saisi sur l'entrée standard pour qu'il n'apparaisse ni dans l'historique ni dans `ps`.
docker login ghcr.io -u ahmedchebbidev --password-stdin < ~/.config/vendora/ghcr-read-token
docker pull ghcr.io/ahmedchebbidev/vendora-server:1.4.0

Le jeton reste hors du dépôt (~/.config/vendora/, coffre de l'équipe) ; un jeton par machine, révocable seul. Une machine de production ne reçoit jamais de jeton write:packages.

Visibilité : github.com › profil › Packages › vendora-server › Package settings › Danger zone › Change visibility (même chose pour vendora-web). Un paquet public se tire sans docker login ; ne le rendre public que si le code des images peut l'être (les images ne contiennent aucun secret : tout passe par les variables d'environnement). Dans Manage Actions access, le dépôt VendoraSystem doit garder le rôle Write (sinon la CI ne peut plus pousser).

Mettre à jour une production : §5 (changer VENDORA_VERSION, pull, up -d). Nettoyer les anciennes images de la machine : docker image prune -a --filter "until=720h". Dans GHCR, supprimer une version se fait depuis la page du paquet (Package settings › Manage versions) ; garder au moins les versions déployées et la précédente.

Construire sans registre : ajouter -f deploy/docker-compose.build.yml et --build (§2) ; les images construites s'appellent vendora-server:local / vendora-web:local (ou VENDORA_LOCAL_TAG) et ne se mélangent pas avec celles du registre. Le pré-staging (§7) construit toujours ses images localement.

10. Redis : facultatif (compteur de débit partagé de l'API publique) ​

Un seul serveur (cas normal, Render compris) : pas de Redis. La limite de débit de chaque clé d'API (requêtes par minute, docs/API-PUBLIQUE.md §5) est tenue en mémoire du serveur (POS_API_RATE_LIMIT_STORE=memory, valeur par défaut). Rien d'autre dans le serveur n'utilise Redis.

Plusieurs nœuds derrière un répartiteur : chaque nœud compterait à part (limite réelle × N). On active alors le compteur partagé Redis (INCR atomique par clé et par minute, expiration 2 minutes, script Lua) :

  1. dans deploy/env/<env>.env : POS_API_RATE_LIMIT_STORE=redis, POS_REDIS_PASSWORD=<mot de passe long> et POS_REDIS_URL=redis://:<même mot de passe>@redis:6379/0 (rediss://… pour un Redis managé en TLS) ;
  2. lancer le compose avec le profil : docker compose -f deploy/docker-compose.prod.yml --env-file deploy/env/prod.env --profile redis up -d (service redis : image redis:7-alpine, --requirepass, aucun port publié, aucune persistance — les compteurs ne vivent qu'une minute) ;
  3. au démarrage, le journal du serveur indique « compteur partagé Redis ». Le garde-fou EnvironmentGuard refuse de démarrer avec POS_API_RATE_LIMIT_STORE=redis sans POS_REDIS_URL (ou avec une autre valeur que memory / redis).

Redis injoignable en cours de route : l'API n'est pas coupée — chaque nœud se replie sur son compteur en mémoire (avertissement journalisé au plus une fois par minute) et revient au compteur partagé dès que Redis répond.

En développement : docker compose --profile redis up -d (Redis sur localhost:6379, sans mot de passe), puis POS_API_RATE_LIMIT_STORE=redis POS_REDIS_URL=redis://localhost:6379/0 au lancement du serveur. Les tests d'intégration démarrent leur propre Redis (Testcontainers, SharedRateLimitRedisIntegrationTest).

Webhooks sortants (docs/API-PUBLIQUE.md §6) : l'expéditeur tourne sur chaque nœud et se partage la file par la base (FOR UPDATE SKIP LOCKED), sans Redis. POS_WEBHOOKS_DISPATCHER=false l'arrête sur un nœud. Hors développement, une URL de webhook doit être en HTTPS et ne peut pas viser une adresse interne (localhost, réseau privé) : prévoir une sortie HTTPS vers Internet depuis le serveur.

Reste à faire le jour où le serveur passera vraiment sur plusieurs nœuds : verrous des tâches planifiées (une seule exécution par cluster) — les tâches actuelles sont idempotentes, mais certaines enverraient leurs emails en double.
