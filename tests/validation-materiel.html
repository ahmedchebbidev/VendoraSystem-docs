Protocole de validation sur matériel réel (spec 11) ​

Objectif : valider sur de vrais appareils ce que les tests automatiques et les émulateurs ne peuvent pas prouver. Chaque essai se fait avec l'écran « Diagnostic matériel » des caisses (menu ⋮ / ⋯) : il mesure, affiche le verdict et produit un rapport copiable à coller dans le tableau de résultats en bas de ce document. Durée estimée : 30 à 45 min par caisse.

Matériel à réunir ​

ÉlémentExemplePour quoi
Terminal Android (≥ Android 8)tablette ou terminal POSapp Android
iPad ou iPhone (iOS 17+)—app iOS (installation via Xcode, signature d'équipe)
Douchette Bluetooth en mode clavier (HID)Zebra, Honeywell, Netum…RG-HW-09
Douchette USB (Android)idemRG-HW-09
Imprimante thermique réseau ESC/POS 80 mm (et 58 mm si possible)Epson TM-T20, Xprinter…RG-HW-02/03/06
Tiroir-caisse RJ11 branché sur l'imprimante—RG-HW-08, RG-CASH-17
Planche d'étiquettes A4 imprimée depuis le back-office (Étiquettes)gabarit 24CA-10
Produits à code-barres réels (EAN-13, EAN-8, UPC-A)eau, café…RG-HW-10

Prérequis : serveur joignable, caisse appairée, un manager avec PIN (Équipe), une imprimante configurée (Réglages imprimante : IP, port 9100, largeur).

1. Douchette HID (Bluetooth, puis USB) — RG-HW-09 ​

Configuration de la douchette : mode clavier, suffixe Entrée, pas de préfixe, clavier français si proposé (sinon US : vérifier les chiffres).

  1. Diagnostic matériel → Douchette → scanner 5 codes différents (dont un code interne 20… d'une étiquette A4).
    • Attendu : pour chaque code, « Reconnu comme scan douchette ✓ », durée de saisie < 100 ms, clé EAN « valide ».
  2. Écran de vente, champ de recherche actif (clavier virtuel ouvert) → scanner un produit.
    • Attendu : le produit est ajouté au panier, le code n'apparaît pas dans la recherche.
  3. Scanner pendant qu'une boîte de dialogue est ouverte (ex. Rapport X).
    • Attendu à constater : comportement actuel connu = scan perdu sur Android (dette tracée) — noter ce qui se passe.
  4. Mettre la douchette en veille puis la réveiller ; scanner.
    • Attendu : reconnexion Bluetooth automatique, premier scan pris en compte.

2. Scan caméra — RG-HW-10 ​

  1. Diagnostic matériel → Caméra → viser un EAN-13 net, bon éclairage.
    • Attendu : détection en < 500 ms, bip + vibration.
  2. Répéter avec : EAN-8, UPC-A, un QR, un Code 128, un code d'étiquette A4 interne, éclairage faible (torche).
    • Attendu : tous détectés ; noter les durées.

3. Imprimante thermique réseau — RG-HW-02/03/04/05/06 ​

  1. Diagnostic matériel → Imprimante → « Ticket de test ».
    • Attendu : ticket complet, accents corrects ou remplacés proprement, coupe partielle, durée affichée.
  2. Encaisser une vente réelle → ticket : n° fiscal + empreinte (spec 15), TVA, paiements, rendu.
  3. Débrancher le câble réseau de l'imprimante, encaisser 2 ventes, rebrancher.
    • Attendu : ventes jamais bloquées (RG-HW-05), tickets imprimés en entier au retour, dans l'ordre.
  4. Ouvrir le capot / retirer le papier pendant une impression.
    • Attendu à constater : statuts COVER_OPEN / PAPER_OUT (RG-HW-06) non implémentés à ce jour — noter le comportement.
  5. Si une imprimante 58 mm est disponible : changer la largeur dans les réglages, réimprimer.
    • Attendu : rien ne déborde (32 colonnes).
  6. Clôture de session → rapport Z imprimé ; réimpression → mention DUPLICATA (sous PIN manager).

4. Tiroir-caisse — RG-HW-08, RG-CASH-17 ​

  1. Diagnostic matériel → Tiroir → PIN manager + motif.
    • Attendu : le tiroir s'ouvre ; message « Tiroir ouvert (approuvé par … ») ; trace visible au back-office (PIN & approbations).
  2. Imprimante éteinte → même essai.
    • Attendu : « Tiroir non ouvert : imprimante injoignable », rien ne s'ouvre au rallumage (pas de file).

5. Son et vibration ​

  1. Diagnostic matériel → Bip : son audible, vibration (Android).

6. Réseau, hors ligne ​

  1. Diagnostic matériel → Réseau : serveur joignable, latence.
  2. Couper le Wi-Fi, encaisser 3 ventes, imprimer, clôturer une session ; rétablir.
    • Attendu : tout fonctionne hors ligne ; au retour, synchro complète (intégrité fiscale « OK » au back-office).

7. Hub local (mDNS / NSD / Bonjour) — spec 10 §4.4 / §8 ​

Le hub est dans les apps depuis le lot 2.6 (élection, relais TCP, rattrapage) et sécurisé aux lots 2.26 / 2.28 (clé LAN du magasin, identité Ed25519 par appareil). Prouvé entre émulateur et simulateur, à rejouer sur 3 appareils physiques (2 Android + 1 iPhone) sur le Wi-Fi du magasin, internet coupé :

  • [ ] Permissions : iOS demande « réseau local » au premier parcours ; Android découvre les pairs (NSD) — attention à l'isolation AP / IGMP des box : les trois appareils doivent se voir dans « Diagnostic matériel › Hub ».
  • [ ] Élection : la caisse marquée principale est hub partout ; statut « temps réel magasin » sur les trois.
  • [ ] Relais < 2 s : un envoi en cuisine depuis le téléphone apparaît sur le KDS / la caisse sans internet.
  • [ ] Chute brutale du hub (kill de l'app, Wi-Fi coupé) : ré-élection ≤ 20 s, rattrapage des événements manqués au retour.
  • [ ] iPhone hub mis en arrière-plan : ré-élection ailleurs en quelques secondes ; retour au premier plan → il rejoint.
  • [ ] Sécurité LAN : un appareil révoqué au back-office est refusé sur le LAN à son prochain Hello (sans serveur) ; un appareil appairé sur un autre magasin ne rejoint pas ; après rotation de la clé LAN, les appareils reprennent au pull suivant. Le diagnostic montre le compteur de refus (rejected).
  • [ ] Identité Ed25519 : chaque appareil a sa clé publique au back-office (GET /pos/lan-peers) ; un appareil dont la clé a été remplacée (ré-appairage) est refusé jusqu'à sa nouvelle synchronisation.

8. Sauvegarde / restauration — bases exclues (RG-AUTH-22, spec 10 §4.5) ​

Déjà prouvé en environnement de développement (lot 2.27, captures) : émulateur Android → bmgr backupnow pos.android = « Backup is not allowed », adb backup = archive vide ; simulateur iPhone → attribut com_apple_backup_excludeItem présent sur le dossier databases et chaque fichier. À refaire une fois sur de vrais appareils :

  • [ ] Android : compte Google de test, Paramètres › Sauvegarde → « Sauvegarder maintenant » ; sur un second appareil, restaurer depuis cette sauvegarde à la configuration → l'app POS est réinstallée vide (écran d'appairage, aucune vente, aucun PIN). Variante : Transfert d'appareil à appareil (câble / Wi-Fi) → idem.
  • [ ] iOS : sauvegarde iCloud (ou Finder) de l'iPhone caisse ; restaurer sur un second iPhone → l'app POS est vide (pas de pos.db, Keychain ThisDeviceOnly non restauré) → ré-appairage, resynchronisation depuis le serveur.
  • [ ] Après restauration : vérifier au back-office que l'ancien appareil est toujours appairé (le révoquer si remplacé).
