Rapport de cohérence inter-specs ​

Relecture croisée des specs 00–14 contre le README (conventions) et ../BRAINSTORMING.md. Date : 2026-10-25. Les corrections mécaniques (nommage, renvois, unités de représentation) ont été appliquées directement dans les fichiers ; les contradictions de fond sont listées en §2 pour arbitrage produit.

1. Corrections appliquées ​

Entités ​

  1. ProductStoreOverride → StoreProductOverride (spec 14, 3 occurrences : RG-MSTORE-04, modèle de données, événements). La spec 02 (catalogue) est propriétaire de l'entité.
  2. Événements associés alignés sur la spec 02 : ProductStoreOverrideSet/ProductStoreOverrideRemoved → StoreProductOverrideSet / StoreProductOverrideCleared (spec 14).

Périmètre fidélité (alignement 06 sur 14) ​

  1. RG-CUST-10 (spec 06) : règle d'accumulation configurée au niveau tenant (plus « par magasin ») + introduction du paramètre tenant loyaltyScope (TENANT défaut / STORE), renvoi explicite à RG-MSTORE-14.
  2. RG-CUST-14 (spec 06) : précision du calcul de solde en mode loyaltyScope = STORE (filtre storeId des LoyaltyEntry).
  3. Modèle de données (spec 06) : LoyaltyConfig et LoyaltyTier passent de storeId à tenantId ; champ loyaltyScope ajouté à LoyaltyConfig.
  4. API (spec 06) : GET/PUT /api/v1/stores/{storeId}/loyalty-config → GET/PUT /api/v1/loyalty-config (tenant-level).
  5. Écran back-office (spec 06) : configuration fidélité marquée « niveau tenant », loyaltyScope ajouté.

Événements de sync — même événement, deux noms ​

  1. DrawerOpened → CashDrawerOpened (spec 12 ; nom émis par les specs 04 et 11).
  2. CustomerCreditChanged → CreditSaleRecorded / CreditPaymentRecorded (noms de la spec 06, propriétaire du journal de crédit) dans les specs 03, 12 et 14.
  3. SaleRefunded, SaleLineVoided, DiscountApplied, PaymentRecorded — événements consommés qui n'existent chez aucun émetteur — remplacés par les événements réels de la spec 03 : SaleCompleted (type=REFUND, paiements et remises dans le payload), SaleVoided, AuditLogAppended (specs 12, 10, et ligne API de la 03 elle-même).
  4. ProductUpserted/PriceChanged → ProductCreated/ProductUpdated/ProductArchived + StoreProductOverrideSet/Cleared + TaxRateUpdated et CustomerUpserted → CustomerCreated/CustomerUpdated (spec 03, liste des événements consommés par l'écran de vente).
  5. CatalogUpdated → événements granulaires de la spec 02 (ProductCreated/Updated/Archived, StoreProductOverrideSet pour la disponibilité « 86 ») — spec 09.
  6. DeviceEnrolled → DevicePaired (spec 10 ; nom défini en spec 01).

Règles & vocabulaire métier ​

  1. Mode de paiement CREDIT → CUSTOMER_CREDIT (spec 06, 11 occurrences) — la spec 03 (RG-SALE-30) est propriétaire de l'énumération des modes de paiement. Le type d'encaissement CREDIT_PAYMENT (règlement d'ardoise, rapport Z) est conservé — voir arbitrage A9.
  2. PMP → CMP (spec 07, toutes occurrences y compris formule newCmp/cmpAvant) — les specs 05 et 12 utilisent CMP. Règle d'arrondi du CMP alignée sur la spec 05 (RG-STOCK-15 : demi-centime au supérieur).
  3. RG-STOCK-04 (spec 05) : ajout des types TRANSFER_DISCREPANCY (requis par la spec 14, RG-MSTORE-11) et SUPPLIER_RETURN (requis par la spec 07, RG-SUP-19) à l'énumération fermée des types de StockMovement. 16 bis. « Formule » (lot formules, 06/11/2026) : en spec 02 / 03 / 05 / 08, « formule » = menu composé vendu (Combo, RG-CAT-88→91, RG-SALE-65→67, RG-STOCK-25, RG-REST-28→31) ; en spec 17, « formule » = abonnement Vendora (Plan). Le code ne mélange jamais les deux (ComboState vs VendoraModules / plans) ; en anglais : meal deal vs plan.

Unités (conventions : centimes / quantityMilli / TVA pour-mille) ​

  1. Spec 03, RG-SALE-05 + modèle SaleLine : quantity: Decimal(3) → quantityMilli: Int (convention spec 05 ; l'affichage reste en décimal 3 décimales).
  2. Spec 03, modèle SaleLine + RG-SALE-22 + CA-04 : vatRate: Decimal(2) en % → vatRatePermille: Int (convention spec 02) ; formule de TVA adaptée (ratePermille / (1000 + ratePermille) — mathématiquement identique) ; exemple round(999×190/1190).
  3. Spec 03, RG-SALE-07 : préfixes balance par défaut 20–21 poids, 22 prix → 21 poids, 22 prix — le préfixe 20 est réservé aux codes-barres internes (spec 02, RG-CAT-42) ; la collision sur 20 est éliminée.

Endpoints API — collisions/doublons ​

  1. Spec 14 : endpoints de surcharge produit réalignés sur ceux de la spec 02 (/api/v1/catalog/stores/{storeId}/overrides[/{productId}]) au lieu de deux jeux de paths concurrents.
  2. Spec 14 : GET /api/v1/reports/consolidated → GET /api/v1/reports/stores/comparison (endpoint défini en spec 12, propriétaire des rapports).
  3. Spec 09 : POST /api/v1/devices/{deviceId}/heartbeats → /heartbeat (endpoint défini en spec 01).

2. Contradictions de fond — à arbitrer par le propriétaire du produit ​

✅ Décisions du 25/10/2026 (session propriétaire produit) ​

Tous les arbitrages ci-dessous ont été tranchés ; les specs ont été mises à jour en conséquence.

  • A1 : hybride — fusion automatique uniquement si téléphone E.164 strictement identique, sinon validation manager ; événement unique CustomerMerged avec champ source: AUTO|MANUAL.
  • A2 : le hub = sérialiseur LAN éphémère (ordre du temps réel local : tables, numéros de retrait), sans autorité de convergence — le serveur cloud reste seul autoritaire.
  • A3 : double numérotation adoptée partout (schéma de la spec 10 : numéro device sans trou + numéro magasin assigné à la sync).
  • A4 : entité unique SalesLayout dès la phase 1 (définie en 13, référencée par 02/03).
  • A5 : ReceiptTemplate = propriété de la spec 11 ; la 13 n'édite que les zones de branding via l'endpoint de la 11.
  • A6 : modèle KioskPreset + DeviceConfig de la 13 adopté ; la 09 fournit le contenu métier du preset.
  • A7 : événement unique UserRoleChanged (01) ; la paire de la 14 est supprimée.
  • A8 : clôture forcée offline sur le device (la 04 fait foi) ; variante back-office online conservée en plus (device perdu/volé).
  • A9 : CREDIT_PAYMENT = ligne dédiée du rapport Z (règlements d'ardoise) dans la 04.
  • A10 : type LOYALTY ajouté au Discount de la 03 (module loyalty).
  • A11 : OrderPaid ≠ OrderPaymentConfirmed — deux faits distincts, documentés dans la 09 et le registre §4.
  • A12 : enveloppe d'événement complète de la spec 10 reportée au README (source de vérité).
  • A13 : endpoints stores = propriété de la 01 ; la 14 ne garde que les règles multi-magasins.
  • Divergences mineures (§2 in fine) : toutes appliquées.
  • + les 10 propositions AMEL adoptées (specs 01→10) et le thème tenant BrandTheme.

A1. Fusion des doublons clients : automatique ou manuelle ? ⚠ priorité haute ​

  • Constat : la spec 06 (RG-CUST-51) fait fusionner automatiquement par le serveur deux fiches au même téléphone créées offline (CustomersMerged). La spec 10 (RG-SYNC-17) dit l'inverse : « fusion manuelle proposée, jamais automatique » (CustomerDuplicateDetected → validation manager → CustomerMerged). Deux noms ET deux workflows.
  • Options : (a) tout automatique (06) ; (b) tout manuel (10) ; (c) hybride.
  • Recommandation : hybride — fusion automatique uniquement sur téléphone E.164 strictement identique (cas de la 06, sans ambiguïté), détection probabiliste → validation manuelle (cas de la 10). Unifier le nom sur CustomerMerged avec un champ source: AUTO|MANUAL.

A2. Le hub local a-t-il une autorité ? ⚠ priorité haute ​

  • Constat : la spec 10 est catégorique (« le hub est un relais, jamais une autorité, il n'assigne pas d'ordre »), mais la spec 08 s'appuie sur lui comme arbitre : « le hub sérialise ; le premier OrderPlaced gagne » (conflit d'ouverture de table) et RG-REST-24 fait allouer la séquence des numéros de retrait par le hub (la spec 09 les alloue au contraire par device avec préfixe).
  • Options : (a) hub strictement relais → 08 doit résoudre les conflits par convergence (préfixes device, premier serverSeq gagne a posteriori) ; (b) accorder au hub un rôle de « sérialiseur LAN éphémère » pour l'UX temps réel, sans autorité de convergence cloud.
  • Recommandation : (b), mais à écrire dans la spec 10 (nouvelle RG) : le hub peut ordonner le temps réel local (tables, numéros de retrait), le serveur cloud reste seul autoritaire pour la convergence — et le comportement en partition (pas de hub) doit être celui de la 09 (préfixe device).

A3. Numérotation des tickets de vente : trois schémas ⚠ priorité haute (fiscal) ​

  • Constat : 03/RG-SALE-40 = séquence par magasin {storeCode}-{YYYYMMDD}-{seq} ; 03/§9 = en réalité séquence par device ; 10/RG-SYNC-13 = <devicePrefix>-<sessionNo>-<seq> sans trou + numéro de magasin assigné par le serveur à la sync.
  • Options : (a) séquence magasin stricte (exigence fiscale possible, mais impose une renumérotation serveur) ; (b) double numérotation de la spec 10.
  • Recommandation : adopter le schéma de la spec 10 partout (il couvre l'offline sans trou ET fournit un numéro magasin) et réécrire RG-SALE-40 en conséquence ; garder la décision finale liée au point ouvert fiscal par pays (§3).

A4. ScreenProfile (spec 02) vs SalesLayout (spec 13) : deux modèles pour les boutons rapides ​

  • Constat : la 02 définit ScreenProfile/QuickButtonPage/QuickButton + événement ScreenProfileUpdated ; la 13 définit SalesLayout/LayoutPage/QuickButton + SalesLayoutUpdated. Même besoin fonctionnel, deux entités, deux événements ; la 03 consomme ScreenProfileUpdated, le DeviceConfig de la 13 pointe salesLayoutId.
  • Options : (a) ScreenProfile (02) = v1, remplacé en phase 4 par SalesLayout (13) ; (b) une seule entité dès la phase 1.
  • Recommandation : (b) — une seule entité, nommée SalesLayout, définie en 13 et référencée par la 02/03 (la double implémentation serait une migration inutile) ; à défaut, documenter explicitement la migration (a).

A5. ReceiptTemplate : défini par la 11 ET la 13, deux endpoints ​

  • Constat : 11 : GET/PUT /stores/{storeId}/receipt-templates/{type} ; 13 : GET/PUT /stores/{id}/receipt-template (singulier, sans type). Deux modèles pour la même entité.
  • Recommandation : propriétaire = spec 11 (contraintes matérielles ESC/POS, types de tickets) ; la 13 n'édite que les zones de branding du template (en-tête/pied, logo) via l'endpoint de la 11. Supprimer l'endpoint singulier de la 13.

A6. Configuration kiosque : KioskConfig (09) vs KioskPreset + DeviceConfig (13) ​

  • Constat : la 09 a un KioskConfig par device (+ GET/PUT /stores/{storeId}/kiosks/{deviceId}/config, événements consommés KioskConfigChanged/KioskDisabled/KioskEnabled qu'aucune spec n'émet) ; la 13 a KioskPreset par magasin + DeviceConfig.kioskPresetId par device (+ KioskPresetUpdated/DeviceConfigUpdated).
  • Recommandation : adopter le modèle de la 13 (preset magasin + surcharge device) ; la 09 garde les champs métier (paymentFlow, timeout, offlineManualConfirm) comme contenu du preset, et consomme KioskPresetUpdated/DeviceConfigUpdated. KioskDisabled/KioskEnabled restent à déclarer comme émis (09 ou 01).

A7. Affectation de rôle par magasin : UserRoleChanged (01) vs StoreRoleAssigned/StoreRoleRevoked (14) ​

  • Constat : même fait métier, deux conventions (un événement générique vs une paire fine).
  • Recommandation : garder UserRoleChanged (01, propriétaire) avec payload {storeId, role|null} — role=null couvrant la révocation — et supprimer la paire de la 14. Décision inverse acceptable, mais un seul nom.

A8. Clôture forcée d'une session de caisse : offline ou online ? ​

  • Constat : la 04 (RG-CASH-18) permet la clôture forcée par un MANAGER sur le device (tout fonctionne offline) ; la 10 (l.178) la décrit comme une « action manager online du back-office ».
  • Recommandation : la 04 fait foi (principe offline-first) ; corriger la 10. La variante back-office online peut exister en plus (device perdu/volé).

A9. Règlement d'ardoise dans la session de caisse : type non défini en 04 ​

  • Constat : la 06 (RG-CUST-23, CA-10) exige que les règlements d'ardoise entrent dans le comptage et le rapport Z comme encaissements de type CREDIT_PAYMENT ; la 04 ne connaît que les mouvements CASH_IN/CASH_OUT et le CA par mode de paiement.
  • Recommandation : ajouter dans la 04 un motif codifié CREDIT_PAYMENT de CASH_IN (ou une ligne dédiée du Z « règlements d'ardoise ») — à trancher avec l'auteur de la 04.

A10. Remise de type LOYALTY : renvoi cassé 06 → 03 ​

  • Constat : la 06 (RG-CUST-12, dépendances) applique le rachat de points « comme une remise de type LOYALTY (spec 03) », mais le type embarqué Discount de la 03 ne connaît que PERCENT|AMOUNT.
  • Recommandation : ajouter LOYALTY (montant en centimes, loyaltyEntryId) au type Discount de la 03, activé par le module loyalty (phase 3).

A11. OrderPaid (08) vs OrderPaymentConfirmed (09) : à confirmer comme deux faits distincts ​

  • Constat : après analyse, ce sont probablement deux événements différents (OrderPaid = l'Order est encaissé via une Sale ; OrderPaymentConfirmed = confirmation d'un paiement TPE au kiosque, avant/à la place du flux caisse), mais aucune spec ne l'explicite et la confusion est probable à l'implémentation.
  • Recommandation : documenter la distinction dans la 09 (et le registre §4 ci-dessous) ; sinon, fusionner sur OrderPaid avec un champ source.

A12. Enveloppe d'événement : README vs spec 10 ​

  • Constat : le README définit 7 champs ; la 10 (canonique) ajoute localSeq, schemaVersion côté client et serverSeq, receivedAt, effectiveAt côté serveur ; les specs 08/11 citent l'enveloppe à 7 champs.
  • Recommandation : mettre à jour le README avec l'enveloppe complète de la 10 (seule source de vérité).

A13. Doublons d'endpoints magasins (01 vs 14) ​

  • Constat : les deux specs définissent GET/POST /stores, GET/PATCH /stores/{storeId}, POST /stores/{storeId}/archive, avec des règles de permission légèrement différentes (la 14 autorise un MANAGER à modifier horaires/TVA par défaut).
  • Recommandation : la 01 est propriétaire des endpoints ; la 14 ne conserve que les règles multi-magasins (contraintes d'archivage RG-MSTORE-02, permission MANAGER sur le PATCH) et renvoie à la 01.

Divergences mineures notées (sans arbitrage bloquant) ​

  • Spec 11 interne : ticket imprimé « < 1 s » (user story) vs « < 2 s » (CA-01) — harmoniser.
  • « Centimes » vs devises à 3 décimales : la maquette 07 affiche des prix TND à 3 décimales (millimes). La convention devrait être reformulée en « entiers dans la plus petite unité de la devise (exposant ISO 4217) » dans le README.
  • Poids : 02 parle de « grammes entiers », 05 de quantityMilli — numériquement identiques pour une unité kg (1 g = 1 millième de kg) ; reformuler la 02 en quantityMilli pour un vocabulaire unique.
  • Format du taux de TVA dans le rapport Z (04, {rate, taxableBase, taxAmount}) : non précisé — utiliser le pour-mille (spec 02).
  • Spec 10 incomplète comme registre des flux : sa liste « consommés/relayés » ignore 7 événements de la 08 et tous ceux des specs 09 et 11 — le registre §4 ci-dessous fait référence en attendant sa mise à jour.
  • StoreCreated/StoreArchived émis à la fois par la 01 et la 14 (noms identiques, pas de conflit) : propriétaire = 01 ; la 14 ajoute StoreUpdated.

5. Verdict global ​

L'ensemble est d'une qualité remarquablement homogène pour 15 auteurs en parallèle : le template est respecté partout, les principes transverses (offline-first, append-only, PIN manager + motif + AuditLog, serveur autoritaire pour la convergence, moteur de calcul KMP partagé) sont appliqués de façon cohérente et quasi unanime, et les montants en centimes sont respectés dans toutes les specs qui en manipulent. Les divergences trouvées étaient en grande majorité périphériques (nommage d'événements entre émetteur et consommateur, doublons d'endpoints, représentation des unités) et ont été corrigées. Les vrais sujets d'arbitrage sont au nombre de quatre : A1 (fusion clients), A2 (autorité du hub local), A3 (numérotation fiscale des tickets) et le trio de chevauchements A4/A5/A6 (customisation 13 vs 02/09/11) — tous tranchables en une session avec les auteurs concernés avant le début de la phase 0/1.
